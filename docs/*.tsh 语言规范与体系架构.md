# TSH（Tree-sitter Highlighting）语言规范与核心架构

> 本文定义 TSH 的目标架构和实现约束。TSH 是独立的语法配置与执行核心，不是 SCM 代码生成器。
> 本文中的“原生查询”指 Tree-sitter 查询引擎内部的 Query/Pattern/Capture/Predicate 数据结构与执行过程；不表示必须生成、保存或加载 `.scm` 文件。

## 1. 核心设计原则

### 1.1 TSH 是唯一配置入口

一个 `.tsh` 文件可以完整描述：

- 语言元信息、扩展名、别名、版本与能力声明。
- Tree-sitter AST 符号规则（ATS）：节点、匿名节点、字段、父子关系、祖先、兄弟、子节点位置、节点文本与错误节点等约束。
- 原生 Tree-sitter 查询块：支持完整的 S-expression 查询表达能力，包括节点模式、字段、匿名节点、量词、锚点、否定字段、Capture 和谓词。
- TSH 原生谓词与动作：字符串/正则匹配、等值判断、多值判断、节点文本判断、Capture 关系判断、优先级/样式/动作元数据。
- Oniguruma 正则规则：单点匹配、begin/end、while、captures、嵌套规则及优先级。
- 样式目录、继承关系、主题、编辑器行为与扩展元数据。

配置完成后，运行时只需要加载对应的 `.tsh` 文件及其 Tree-sitter Language。不得要求用户再创建或维护配套 `.scm` 文件。

### 1.2 严禁 SCM 中间产物

以下做法均禁止：

- 将 ATS 声明拼接、翻译或序列化成 S-expression/SCM 文本。
- 将 TSH 的查询结构导出成临时 `.scm` 文件、缓存文件或 assets 文件。
- 通过“TSH → SCM → Tree-sitter Query”作为 ATS 的编译路径。
- 在运行时从磁盘查找 TSH 自动生成的 SCM 文件。
- 为了复用 SCM 语法而把 TSH 的节点关系、谓词或样式信息编码进伪造的 Capture 名称。

允许在内存中保留用户直接写在 TSH 原生查询区块中的查询源码，作为 Tree-sitter 原生 Query Parser 的输入；这只是源码输入缓冲，不是生成物或独立文件。解析后由 Tree-sitter 查询引擎构建其内部 Query 结构并执行。

### 1.3 两种查询表达能力并存

TSH 同时提供两条 AST 查询定义路径：

1. **ATS 声明式区块**：TSH 自己的强类型节点选择 DSL，编译为 TSH 原生 AST 执行计划；不转换成 SCM。
2. **原生查询区块**：用户在 TSH 中直接编写完整 Tree-sitter S-expression 查询块，由 Tree-sitter Query Parser 直接解析为原生 Query 对象。

两者共享 Tree-sitter AST、谓词执行扩展、Capture 语义和最终 Span 合成器。ATS 与谓词是不同层次：ATS 负责节点/关系匹配，谓词负责对已匹配节点或 Capture 进行条件判断，不得互相混淆。

兼容旧式独立 `.scm` 文件时，只允许把用户提供的 SCM 源码作为可选的直接输入交给同一原生查询解析器；不得要求它存在，也不得把 TSH 生成 SCM。

## 2. 总体架构

```text
.tsh source
   |
   v
TshLexer -> TshParser -> TshDocument (typed AST + source spans)
                            |
                            v
                      TshValidator
          (schema / types / references / language symbols /
           predicate signatures / conflicts / diagnostics)
                            |
                            v
                       TshCompiler
          +-----------------+--------------------+
          |                 |                    |
          v                 v                    v
   ATS Compiler       Native Query Compiler   Regex Compiler
          |                 |                    |
   AtsExecutionPlan   TSQuery per query block  Onig compiled rules
          |           (direct native parser)       |
          +-----------------+--------------------+
                            |
                            v
                    Immutable TshProgram
             (styles / themes / capture maps /
              query plans / regex plans / editor metadata)
                            |
                            v
                       TshRuntime
             +--------------+----------------+
             |              |                |
             v              v                v
       ATS executor   Tree-sitter Query   Oniguruma runner
                      + TSH predicates
             |              |                |
             +--------------+----------------+
                            |
                            v
                   Candidate Span stream
                            |
                            v
                Priority / nesting / overlap resolver
                            |
                            v
                 packed Span buffer -> JNI -> Kotlin
```

## 3. 词法、语法与语义模型

### 3.1 Parser 产物

Parser 必须输出与源文件坐标绑定的强类型 AST，而不是在解析时直接修改运行时 Grammar：

- 每个声明保留 source range、行列、原始标识符和文档顺序。
- 每个属性具有明确类型、所属上下文、重复策略、默认值与版本。
- 正则、字符串、S-expression 查询源码均使用独立 AST 节点类型。
- 解析错误、语义错误和编译错误使用统一 Diagnostic 模型。
- Parser 不执行 Tree-sitter 查询编译、不执行 Oniguruma 编译、不分配最终 Style ID。

### 3.2 Validator

Validator 在编译前完成静态检查：

- 未知字段、重复字段、非法类型、非法枚举值。
- Style、Theme、Query、Capture、Rule、Repository、Include 等引用完整性。
- 重复 ID、循环继承、循环 include、冲突声明。
- 节点类型和字段名是否存在于传入的 TSLanguage。
- 谓词名称、参数数量、参数类型与可用 Capture 是否正确。
- Query block 与语言版本/能力的兼容性。
- Regex Capture 数字组、命名组、别名冲突。
- 不支持的语义必须明确报错，不能“解析成功但运行时忽略”。

### 3.3 Compiler 输出

编译器输出一个不可变的 `TshProgram`。Parser AST 与执行时结构分离，编译器负责解析引用、分配 ID、编译正则和查询、构建索引与验证执行计划。

编译必须是事务式的：所有阶段成功后才发布新 Grammar；失败时保留旧版本，不得注册半成品。

## 4. ATS：原生 AST 选择器

ATS 是独立于 S-expression 查询语法的 TSH 声明式节点匹配系统。

### 4.1 节点选择维度

ATS 至少应支持：

- 当前节点：具名节点、匿名节点、符号 ID、节点类型集合。
- 节点状态：named、missing、extra、error、has_error。
- 字段：当前节点所在字段、字段存在性、字段值节点。
- 关系：parent、ancestor、child、descendant、previous/next sibling。
- 位置：first/last child、child index、named child index、相邻节点关系。
- 结构：子节点数量、指定字段子节点、节点范围、父节点类型路径。
- 文本：节点文本长度、文本前缀/后缀、精确文本或文本正则（走独立谓词阶段）。
- 执行控制：enabled、priority、order、overlap、style、action、capture。

ATS 规则编译为专用结构化执行计划。执行器基于 Tree-sitter 的 TSNode/TSTreeCursor API 遍历和判断，不生成 S-expression 字符串。

### 4.2 ATS 执行优化

- 按 target symbol 建立索引，避免每个节点遍历全部规则。
- 按 field、parent symbol、node flags 进一步分桶。
- 规则中不存在的约束不进行额外 API 调用。
- 只在规则确实需要文本条件时读取节点文本。
- 对查询范围、增量编辑范围进行剪枝。
- 保证对同一节点的多条规则都可命中；最终冲突交给统一 Span Resolver。

## 5. 原生 Tree-sitter 查询区块

### 5.1 完整查询源码直接编译

TSH 中的原生查询区块允许完整 S-expression 查询：

- 节点模式、匿名节点、字段约束。
- `.` 锚点、`!` 否定字段。
- Capture、量词和分组。
- Tree-sitter 版本支持的原生谓词与指令。
- TSH 扩展谓词和 TSH Capture 元数据。

每个 query block 是独立编译单元，拥有自己的 TSQuery、Capture 映射、优先级、启用状态、ID 和诊断位置。禁止把多个区块拼成一个大字符串来丢失区块边界和元数据。

编译流程是：TshParser 读取用户原文 → Validator 检查 TSH 元数据 → Tree-sitter 原生 Query Parser 直接解析该原文 → 保存 TSQuery 对象。没有 SCM 文件生成、文件缓存或 ATS 到 SCM 的翻译步骤。

### 5.2 原生 Query 的扩展边界

优先复用 Tree-sitter 现有 Query Parser、Query Pattern、Capture 和 Cursor。若需要新的 TSH 谓词，应在 Tree-sitter 查询执行/谓词消费层增加明确的谓词类型和执行回调，而不是将谓词伪装成 ATS 条件，也不能靠生成额外 SCM 指令绕过。

需要支持的 TSH 谓词族（按版本逐步实现）：

- 文本匹配：match / not-match。
- 等值：eq / not-eq。
- 多值：any-of / not-any-of。
- Capture 关系：capture-eq / capture-match。
- 节点属性：is-named / is-missing / is-error / has-error。
- 长度和范围：text-length、byte-range 等。
- 元数据指令：set priority、style、action、overlap、layer 等。

谓词必须有注册表、参数签名、类型检查、执行器、错误码和测试。未知谓词不得静默通过。

### 5.3 原生 Query 与 ATS 不互相转换

ATS 不编译成查询字符串；原生 Query 不反向解析成 ATS。二者只共享底层 Tree-sitter 节点对象和后续的 Capture/Span 输出模型。

## 6. Capture 与样式映射

每个 Query block 拥有独立 Capture 表。Capture 名称不是 Style ID，也不应被当作唯一样式来源。

建议编译期结构：

- QueryProgram：query_id、TSQuery、priority、declaration_order、enabled。
- CaptureBinding：capture_id、style_id、action_id、priority_delta、flags、layer、overlap_policy。
- PatternMetadata：pattern_index、priority、action_id、metadata。
- StyleCatalog：稳定的 style name 与内部 style ID。
- ActionCatalog：稳定的 action name 与内部 action ID。

一个 Capture 可以绑定样式、动作、优先级和行为；多个 Capture 可以映射到同一 Style；同一节点可以由多个 Capture 产生候选 Span。

执行时通过 `ts_query_capture_name_for_id` / 原生 Capture ID 获取 Capture，再通过 QueryProgram 自己的 CaptureBinding 表查找元数据。禁止只用全局 `style_name_to_id[capture_name]` 推断所有语义。

## 7. 正则管道

正则管道独立使用 Oniguruma，不转换为 Tree-sitter Query。

必须逐步完整实现：

- match / begin-end / while。
- captures、beginCaptures、endCaptures、whileCaptures。
- repository 与 include 别名、循环检测。
- 嵌套规则与规则优先级。
- applyEndPatternLast 的真实匹配优先级。
- Unicode、UTF-16LE、CRLF/LF/CR、空文档与 EOF。
- 零宽匹配防止死循环。
- 每个正则资源有明确 RAII 生命周期。

不支持的 TextMate 语义必须在 Validator 阶段拒绝，不能接受 DSL 后由 Runtime 忽略。

## 8. 双管道调度与 Span 合成

AST/Query 管道与 Regex 管道并行产出 CandidateSpan。Span 的统一结构应携带：

- start/end byte（统一 Tree-sitter UTF-8 byte offset）。
- style_id、action_id、flags。
- source_kind（ATS / NativeQuery / Regex / Monarch）。
- priority、declaration_order、layer。
- overlap policy 与可选 pattern/rule id。

注意：Tree-sitter 节点范围是 UTF-8 byte offset，而当前 Oniguruma 输入使用 UTF-16LE offset。合并前必须通过行/列或预计算映射将 UTF-16 offset 正确转换为 UTF-8 byte offset；禁止把 UTF-16 偏移直接当作 Tree-sitter byte offset。转换表按文档版本缓存，并随增量编辑失效/更新。

Span Resolver 统一处理优先级、相同范围覆盖、嵌套、重叠许可、声明顺序和动作元数据。不得让 ATS、Query、Regex 各自实现互相矛盾的冲突规则。

JNI 输出协议必须带版本号或固定 ABI 定义，并包含 action_id；不得通过压缩字段丢失优先级或来源信息。Kotlin 层只负责消费结果，不重新推断语义。

## 9. 主题与编辑器行为

- Style Catalog 只保存语义身份，不硬编码主题颜色。
- Theme/Scheme 通过 Style ID 解析颜色、字体、修饰和 UI token。
- 主题继承需检测循环并在编译时完成。
- Editor metadata（注释、括号、自动闭合、缩进、on-enter、触发字符等）由独立模块解析和消费。
- 不把编辑器行为塞进 AST Query 或 Regex Runtime。
- 不包含 Outline/Folding 功能；本项目当前范围不实现该子系统。

## 10. 内存、并发与生命周期

- TshProgram 发布后不可变；运行时只持有 `shared_ptr<const TshProgram>`。
- TSQuery、Oniguruma regex、谓词对象使用 RAII 封装，禁止裸指针所有权分散。
- 每次高亮使用独立 TSQueryCursor；不得跨线程共享 cursor。
- 语言对象由 Tree-sitter Language 生命周期管理，TSH 不释放外部 TSLanguage。
- Oniguruma 初始化/结束由进程级 Runtime 管理，不随单个 Grammar 重复初始化。
- 新配置编译失败不得破坏已注册旧配置。
- 并发编译诊断必须绑定当前编译调用，不依赖全局 last-error 状态。

## 11. 推荐 TSH 文件组织形式

以下是结构示意，不代表所有字段已在当前版本实现：

```tsh
tsh {
  version: 2
  language: {
    id: "example"
    extensions: [".ex"]
  }

  styles: {
    keyword: { tags: ["keyword"] }
    function: { tags: ["entity", "function"] }
    string: { tags: ["string"] }
  }

  schemes: {
    default: {
      isDark: false
      colors: {
        keyword: { light: "#8959A8", dark: "#C586C0" }
        function: { light: "#795E26", dark: "#DCDCAA" }
        string: { light: "#A31515", dark: "#CE9178" }
      }
    }
  }

  // TSH-native ATS: never serialized to SCM.
  ast: [
    {
      id: "function-name"
      node: "identifier"
      parent: "function_declaration"
      field: "name"
      style: "function"
      priority: 20
    }
  ]

  // Full native Tree-sitter query source, parsed directly by Tree-sitter.
  treeSitter: {
    queries: [
      {
        id: "declarations"
        priority: 10
        source: "(function_declaration name: (identifier) @function)"
        captures: {
          function: { style: "function", action: "navigate-definition" }
        }
      }
    ]
  }

  // Independent Oniguruma pipeline.
  contains: [
    {
      id: "quoted-string"
      begin: /"/
      end: /"/
      style: "string"
      contentStyle: "string"
    }
  ]
}
```

注意：示例只用于说明区块职责。字段的可用状态必须以版本化 Schema 和实际实现为准；未实现字段不能被文档宣称为已支持。

## 12. 分阶段重构路线

### Phase A — 结构基础
- 将 Parser AST、Validator、Compiler、Runtime 的职责分离。
- 把 `TshGrammar` 重命名/演进为不可变 `TshProgram`。
- 用 RAII 管理 TSQuery 与 Oniguruma 对象。
- 引入统一 Diagnostic、SourceRange、编译产物版本。

### Phase B — ATS 原生执行器
- 扩展 ATS 类型系统与节点关系。
- 构建 symbol/field 索引。
- 完成 ATS 规则编译、执行和测试。
- 确保 ATS 路径完全没有 SCM 字符串生成代码。

### Phase C — 原生 Query 子系统
- 从单个聚合 `dynamic_ts_query` 改成多个独立 QueryProgram。
- 每个 QueryProgram 独立 TSQuery、CaptureBinding、PatternMetadata。
- 验证完整 S-expression 查询直接进入 Tree-sitter 原生解析器。
- 在 Tree-sitter 查询谓词层添加 TSH 扩展谓词，保持 ATS 与谓词职责独立。

### Phase D — Regex 完整语义
- 完成 while/whileCaptures、applyEndPatternLast。
- 完成正确的跨行扫描和嵌套规则优先级。
- 完成 UTF-16 到 UTF-8 offset 映射。

### Phase E — Span/JNI/Kotlin
- 统一 ATS、Query、Regex 的 CandidateSpan。
- 完成 action_id、priority、source_kind 等稳定 ABI。
- Kotlin 侧按 ABI 消费，不进行语义补偿。

### Phase F — 首轮验证与 APK
- C++ 单元测试：ATS、原生 Query、谓词、Capture、Regex、Span Resolver。
- Tree-sitter 多语言测试：至少覆盖匿名节点、字段、锚点、否定字段、量词和谓词。
- JNI/Kotlin 集成测试：offset、style/action、空文档、Unicode、增量编辑。
- Android Debug APK 构建并安装运行。
- 记录构建命令、commit SHA、ABI、测试结果和 APK artifact。

## 13. 验收标准

只有满足以下条件才可称为 TSH 核心架构完成：

1. ATS 规则直接执行结构化 ATS 计划，代码路径中不存在 ATS→SCM 转换。
2. TSH 原生查询区块独立编译为原生 TSQuery，不产生 SCM 文件。
3. 多个查询块的 Capture 映射、优先级、动作 ID 不互相污染。
4. TSH 扩展谓词在 Tree-sitter 查询执行/谓词消费层真正执行，而非只被 Parser 接受。
5. ATS、Query、Regex 输出由统一 Span Resolver 合成。
6. UTF-8/UTF-16 offset 转换正确，Emoji、补充平面字符、CRLF 测试通过。
7. 未实现语义明确报错，不存在静默降级。
8. 完成 native 测试、Kotlin 集成测试和 Android APK 构建。
9. 用户只需提供 `.tsh` 与 Tree-sitter Language，不需要配套 `.scm` 文件。

---

**架构底线：TSH 是配置语言和运行时核心；Tree-sitter 是 AST 与原生 Query 引擎；Oniguruma 是正则引擎。三者通过结构化执行计划和统一 Span 协议协作。SCM 只是一种可选的原生查询书写形式，不是 TSH 的中间语言、构建产物或运行时文件依赖。**
