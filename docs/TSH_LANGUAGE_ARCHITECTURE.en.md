# TSH Language Specification and Core Architecture

> This document defines the target architecture and implementation constraints of TSH. TSH is an independent syntax-configuration and execution core, not an SCM code generator.
>
> “Native Query” means the Query/Pattern/Capture/Predicate data structures and execution process inside Tree-sitter's query engine. It does not mean that a `.scm` file must be generated, stored, or loaded.

## 1. Core Design Principles

### 1.1 TSH Is the Single Configuration Entry

A single `.tsh` file can describe:

- Language metadata, extensions, aliases, versions, and capability declarations.
- Tree-sitter AST symbol rules (ATS): named/anonymous nodes, fields, parent-child relationships, ancestors, siblings, child positions, node text, and error-node constraints.
- Native Tree-sitter Query blocks: node patterns, fields, anonymous nodes, quantifiers, anchors, negated fields, captures, and predicates.
- TSH-native predicates/actions: string/Regex matching, equality, multi-value checks, node-text checks, Capture relationships, priority/style/action metadata.
- Oniguruma Regex rules: single matches, begin/end, while, captures, nested rules, and priority.
- Style catalogs, inheritance, themes, editor behavior, and extension metadata.

At runtime, loading the corresponding `.tsh` file and Tree-sitter Language should be sufficient. Users must not be required to create or maintain companion `.scm` files.

### 1.2 No SCM Intermediate Artifacts

The following are prohibited:

- Concatenating, translating, or serializing ATS declarations into S-expression/SCM text.
- Exporting TSH query structures into temporary `.scm`, cache, or assets files.
- Using “TSH -> SCM -> Tree-sitter Query” as the ATS compilation path.
- Searching the filesystem at runtime for SCM files generated by TSH.
- Encoding TSH node relationships, predicates, or styles into fabricated Capture names merely to reuse SCM syntax.

It is permitted to retain Query source written directly by the user in a TSH native-query block in memory and pass it to Tree-sitter's native Query parser. This is an input buffer, not a generated artifact or standalone file. Tree-sitter then builds and executes its internal Query structures.

### 1.3 Two Query-Expression Paths Coexist

TSH provides two AST-query definition paths:

1. **ATS declarative block:** TSH's own strongly typed node-selection DSL, compiled into a TSH-native AST execution plan; it is not converted to SCM.
2. **Native Query block:** users write complete Tree-sitter S-expression Query blocks directly in TSH; Tree-sitter's Query parser parses them into native Query objects.

Both share the Tree-sitter AST, predicate extensions, Capture semantics, and final Span composer. ATS and predicates are different layers: ATS selects nodes/relationships; predicates conditionally evaluate already matched nodes or Captures.

For compatibility with legacy standalone `.scm` files, user-supplied SCM source may optionally be passed directly to the same native Query parser. Its existence must never be required, and TSH must never generate SCM.

## 2. Overall Architecture

```text
.tsh source
   |
   v
TshLexer -> TshParser -> TshDocument (typed AST + source spans)
                            |
                            v
                      TshValidator
          (schema / types / references / language symbols /
           predicate signatures / conflicts / diagnostics)
                            |
                            v
                       TshCompiler
          +-----------------+--------------------+
          |                 |                    |
          v                 v                    v
   ATS Compiler       Native Query Compiler   Regex Compiler
          |                 |                    |
   AtsExecutionPlan   TSQuery per query block  Onig compiled rules
          |           (direct native parser)       |
          +-----------------+--------------------+
                            |
                            v
                    Immutable TshProgram
             (styles / themes / capture maps /
              query plans / regex plans / editor metadata)
                            |
                            v
                       TshRuntime
             +--------------+----------------+
             |              |                |
             v              v                v
       ATS executor   Tree-sitter Query   Oniguruma runner
                      + TSH predicates
             |              |                |
             +--------------+----------------+
                            |
                            v
                   Candidate Span stream
                            |
                            v
                Priority / nesting / overlap resolver
                            |
                            v
                 packed Span buffer -> JNI -> Kotlin
```

## 3. Runtime and Ownership Boundaries

- The `.tsh` document is the source of language-specific rules and theme data.
- Grammar modules provide compiled Tree-sitter language definitions.
- ATS selectors and native Query programs execute against the target grammar/tree.
- Regex/Oniguruma executes independently over text windows.
- Both pipelines emit normalized match/capture results; a resolver handles priority and overlap.
- Kotlin/JNI adapters must preserve document version, coordinate system, object identity, and Native resource ownership.
- The host Renderer owns final drawing; Native output or RenderPlan creation alone is not proof of visible rendering.

## 4. Compatibility and Implementation Status

Do not describe a planned parser, validator, compiler stage, or runtime capability as implemented without source evidence. Separate design status, source implementation, build verification, automated test verification, and real-device verification. Existing compatibility entry points must not be removed or have their ABI changed without migration and regression evidence.
